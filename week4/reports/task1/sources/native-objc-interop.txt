1: Interoperability with Swift/Objective-C
2: 
3: The Objective-C libraries import is in Beta . All Kotlin declarations generated by the cinterop tool from Objective-C libraries should have the @ExperimentalForeignApi annotation.
4: 
5: Native platform libraries shipped with Kotlin/Native (like Foundation, UIKit, and POSIX) require opt-in only for some APIs.
6: 
7: Kotlin/Native provides indirect interoperability with Swift through Objective-C. This document covers how you can use Kotlin declarations in Swift/Objective-C code and Objective-C declarations in Kotlin code.
8: 
9: Some other resources you might find useful:
10: 
11: The Kotlin-Swift interopedia , a collection of examples on how to use Kotlin declarations in Swift code.
12: 
13: The Integration with Swift/Objective-C ARC section, covering the details of integration between Kotlin's tracing GC and Objective-C's ARC.

33: Hide Kotlin declarations from Objective-C and Swift
34: 
35: To make your Kotlin code more Swift/Objective-C-friendly, use the @HiddenFromObjC annotation to hide a Kotlin declaration from Objective-C and Swift. It disables the function or property export to Objective-C.
36: 
37: Alternatively, you can mark Kotlin declarations with the internal modifier to restrict their visibility in the compilation module. Use @HiddenFromObjC if you want to hide the Kotlin declaration from Objective-C and Swift while keeping it visible to other Kotlin modules.
38: 
39: See an example in the Kotlin-Swift interopedia .
40: 
41: Use refining in Swift
42: 
43: @ShouldRefineInSwift helps to replace a Kotlin declaration with a wrapper written in Swift. The annotation marks a function or property as swift_private in the generated Objective-C API. Such declarations get the __ prefix, which makes them invisible from Swift.
44: 
45: You can still use these declarations in your Swift code to create a Swift-friendly API, but they won't be suggested in the Xcode autocomplete.
46: 
47: For more information on refining Objective-C declarations in Swift, see the official Apple documentation .
48: 
49: For an example on how to use the @ShouldRefineInSwift annotation, see the Kotlin-Swift interopedia .
50: 
51: Change declaration names
52: 
53: To avoid renaming Kotlin declarations, use the @ObjCName annotation. It instructs the Kotlin compiler to use the custom Objective-C and Swift name for the annotated class, interface, or another Kotlin entity:
54: 
55: @ObjCName(swiftName = "MySwiftArray")
56: class MyKotlinArray {
57:     @ObjCName("index")
58:     fun indexOf(@ObjCName("of") element: String): Int = TODO()
59: }
60: 
61: // Usage with the ObjCName annotations
62: let array = MySwiftArray()
63: let index = array.index(of: "element")
64: 
65: See another example in the Kotlin-Swift interopedia .

67: Provide documentation with KDoc comments
68: 
69: Documentation is essential for understanding any API. Providing documentation for the shared Kotlin API allows you to communicate with its users on matters of usage, dos and don'ts, and so on.
70: 
71: When generating Objective-C headers, KDoc comments from Kotlin code are translated into corresponding Objective-C comments. For example, the following Kotlin code with KDoc:
72: 
73: /**
74:  * Prints the sum of the arguments.
75:  * Properly handles the case when the sum doesn't fit in 32-bit integer.
76:  */
77: fun printSum(a: Int, b: Int) = println(a.toLong() + b)
78: 
79: Will produce an Objective-C header with the corresponding comment:
80: 
81: /**
82:  * Prints the sum of the arguments.
83:  * Properly handles the case when the sum doesn't fit in 32-bit integer.
84:  */
85: + (void)printSumA:(int32_t)a b:(int32_t)b __attribute__((swift_name("printSum(a:b:)")));
86: 
87: KDoc comments are embedded into klibs and extracted from klibs into the produced Apple frameworks. As a result, comments on classes and methods appear during autocompletion, for example in Xcode. If you go to the definition of functions in the .h file, you'll see comments on @param , @return , and similar tags.
88: 
89: Known limitations:
90: 
91: Dependency documentation is not exported unless it is compiled with the -Xexport-kdoc option. Libraries compiled with this compiler option might be incompatible with other compiler versions.
92: 
93: KDoc comments are mostly exported as is, but many KDoc block tags, such as @property , are not supported.
94: 
95: If necessary, you can disable the export of KDoc comments from klibs to the produced Apple frameworks in the binaries {} block of your Gradle build file:
96: 
97: // build.gradle.kts
98: import org.jetbrains.kotlin.gradle.ExperimentalKotlinGradlePluginApi
99: 
100: kotlin {
101:     iosArm64 {
102:         binaries {
103:             framework {
104:                 baseName = "sdk"
105:                 @OptIn(ExperimentalKotlinGradlePluginApi::class)
106:                 exportKdoc.set(false)
107:             }
108:         }
109:     }
110: }

113: 
114: The table below shows how Kotlin concepts are mapped to Swift/Objective-C and vice versa.
115: 
116: "->" and "<-" indicate that mapping only goes one way.
117: 
118: Kotlin | Swift | Objective-C | Notes
119: class | class | @interface | note
120: interface | protocol | @protocol | 
121: constructor / create | Initializer | Initializer | note
122: Property | Property | Property | note 1 , note 2
123: Method | Method | Method | note 1 , note 2
124: enum class | class | @interface | note
125: suspend -> | completionHandler: / async | completionHandler: | note 1 , note 2
126: @Throws fun | throws | error:(NSError**)error | note
127: Extension | Extension | Category member | note
128: companion member <- | Class method or property | Class method or property | 
129: null | nil | nil | 
130: Singleton | shared or companion property | shared or companion property | note
131: Primitive type | Primitive type / NSNumber |  | note
132: Unit return type | Void | void | 
133: String | String | NSString | note
134: String | NSMutableString | NSMutableString | note
135: List | Array | NSArray | 
136: MutableList | NSMutableArray | NSMutableArray |

144: Classes
145: 
146: Name translation
147: 
148: Objective-C classes are imported into Kotlin with their original names. Protocols are imported as interfaces with a Protocol name suffix, for example, @protocol Foo -> interface FooProtocol . These classes and interfaces are placed into a package specified in build configuration ( platform.* packages for preconfigured system frameworks).
149: 
150: The names of Kotlin classes and interfaces are prefixed when imported to Objective-C. The prefix is derived from the framework name.
151: 
152: Objective-C does not support packages in a framework. If the Kotlin compiler finds Kotlin classes in the same framework which have the same name but different packages, it renames them. This algorithm is not stable yet and can change between Kotlin releases. To work around this, you can rename the conflicting Kotlin classes in the framework.
153: 
154: Strong linking
155: 
156: Whenever you use an Objective-C class in the Kotlin source, it's marked as a strongly linked symbol. The resulting build artifact mentions related symbols as strong external references.
157: 
158: This means that the app tries to link symbols during the launch dynamically, and if they are unavailable, the app crashes. The crash happens even if symbols were never used. Symbols might be unavailable on a particular device or OS version.
159: 
160: To work around this issue and avoid "Symbol not found" errors, use a Swift or Objective-C wrapper that checks if the class is actually available. See how this workaround was implemented in the Compose Multiplatform framework .
161: 
162: Initializers
163: 
164: A Swift/Objective-C initializer is imported to Kotlin as constructors or as factory methods named create . The latter happens with initializers declared in the Objective-C category or as a Swift extension, because Kotlin has no concept of extension constructors.
165: 
166: Before importing Swift initializers to Kotlin, don't forget to annotate them with @objc .
167: 
168: Kotlin constructors are imported as initializers to Swift/Objective-C.
169: 
170: Setters
171: 
172: Writeable Objective-C properties overriding read-only properties of the superclass are represented as the setFoo() method for the property foo . The same goes for a protocol's read-only properties that are implemented as mutable.
173: 
174: Top-level functions and properties
175: 
176: Top-level Kotlin functions and properties are accessible as members of special classes. Each Kotlin file is translated into such a class, for example:
177: 
178: // MyLibraryUtils.kt
179: package my.library
180: 
181: fun foo() {}
182: 
183: You can then call the foo() function from Swift like this:
184: 
185: MyLibraryUtilsKt.foo()
186: 
187: See a collection of examples on accessing top-level Kotlin declarations in the Kotlin-Swift interopedia:

195: Method names translation
196: 
197: Generally, Swift argument labels and Objective-C selector pieces are mapped to Kotlin parameter names. These two concepts have different semantics, so sometimes Swift/Objective-C methods can be imported with a clashing Kotlin signature. In this case, the clashing methods can be called from Kotlin using named arguments, for example:
198: 
199: [player moveTo:LEFT byMeters:17]
200: [player moveTo:UP byInches:42]
201: 
202: In Kotlin, it's:
203: 
204: player.moveTo(LEFT, byMeters = 17)
205: player.moveTo(UP, byInches = 42)
206: 
207: Here's how the kotlin.Any functions are mapped to Swift/Objective-C:
208: 
209: Kotlin | Swift | Objective-C
210: equals() | isEquals(_:) | isEquals:
211: hashCode() | hash | hash
212: toString() | description | description
213: 
214: See an example with data classes in the Kotlin-Swift interopedia .
215: 
216: You can specify a more idiomatic name in Swift or Objective-C, instead of renaming the Kotlin declaration with the @ObjCName annotation .
217: 
218: Errors and exceptions
219: 
220: All Kotlin exceptions are unchecked, meaning that errors are caught at runtime. However, Swift has only checked errors that are handled at compile time. So, if Swift or Objective-C code calls a Kotlin method that throws an exception, the Kotlin method should be marked with the @Throws annotation, specifying a list of "expected" exception classes.
221: 
222: When compiling to the Swift/Objective-C framework, non- suspend functions that have or inherit the @Throws annotation are represented as NSError* -producing methods in Objective-C and as throws methods in Swift. Representations for suspend functions always have an NSError* / Error parameter in the completion handler.
223: 
224: When a Kotlin function called from Swift/Objective-C code throws an exception which is an instance of one of the classes specified with @Throws or their subclasses, the exception is propagated as an NSError . Other Kotlin exceptions reaching Swift/Objective-C are considered unhandled and cause program termination.
225: 
226: suspend functions without @Throws propagate only CancellationException (as NSError ). Non- suspend functions without @Throws don't propagate Kotlin exceptions at all.
227: 
228: Note that the opposite reversed translation is not implemented yet: Swift/Objective-C error-throwing methods aren't imported to Kotlin as exception-throwing.
229: 
230: See an example in the Kotlin-Swift interopedia .
231: 
232: Enums
233: 
234: Kotlin enums are imported into Objective-C as @interface and into Swift as class . These data structures have properties corresponding to each enum value. Consider this Kotlin code:
235: 
236: // Kotlin
237: enum class Colors {
238:     RED, GREEN, BLUE
239: }
240: 
241: You can access the properties of this enum class from Swift as follows:
242: 
243: // Swift
244: Colors.red
245: Colors.green
246: Colors.blue
247: 
248: To use variables of a Kotlin enum in a Swift switch statement, provide a default statement to prevent a compilation error:
249: 
250: switch color {
251:     case .red: print("It's red")
252:     case .green: print("It's green")
253:     case .blue: print("It's blue")
254:     default: fatalError("No such color")
255: }
256: 
257: See another example in the Kotlin-Swift interopedia .

259: Suspending functions
260: 
261: Kotlin's suspending functions ( suspend ) are presented in the generated Objective-C headers as functions with callbacks, or completion handlers in Swift/Objective-C terminology.
262: 
263: Starting from Swift 5.5, Kotlin's suspend functions are also available for calling from Swift as async functions without using the completion handlers. Currently, this functionality is highly experimental and has certain limitations. See this YouTrack issue for details.
264: 
265: Learn more about the async / await mechanism in the Swift documentation .
266: 
267: See an example and recommendations on third-party libraries that implement the same functionality in the Kotlin-Swift interopedia .

269: Extensions and category members
270: 
271: Members of Objective-C categories and Swift extensions are generally imported to Kotlin as extensions. That's why these declarations can't be overridden in Kotlin, and the extension initializers aren't available as Kotlin constructors.
272: 
273: Currently, there are two exceptions. Starting with Kotlin 1.8.20, category members that are declared in the same headers as the NSView class (from the AppKit framework) or UIView classes (from the UIKit framework) are imported as members of these classes. This means that you can override methods that subclass from NSView or UIView.
274:

295: Kotlin singletons
296: 
297: Kotlin singleton (made with an object declaration, including companion object ) is imported to Swift/Objective-C as a class with a single instance.
298: 
299: The instance is available through the shared and companion properties.
300: 
301: For the following Kotlin code:

303: object MyObject {
304:     val x = "Some value"

309:         val x = "Some value"

311: }

314: 
315: MyObject.shared
316: MyObject.shared.x
317: MyClass.companion

328: Primitive types
329: 
330: Kotlin primitive type boxes are mapped to special Swift/Objective-C classes. For example, the kotlin.Int box is represented as the KotlinInt class instance in Swift (or the ${prefix}Int instance in Objective-C, where prefix is the framework's name prefix). These classes are derived from NSNumber , so the instances are proper NSNumber s supporting all corresponding operations.
331: 
332: The NSNumber type is not automatically translated to Kotlin primitive types when used as a Swift/Objective-C parameter type or return value. The reason is that the NSNumber type doesn't provide enough information about a wrapped primitive value type, for example, NSNumber is statically not known to be Byte , Boolean , or Double . So Kotlin primitive values should be cast to and from NSNumber manually .
333: 
334: Strings
335: 
336: When a Kotlin String is passed to Swift, it's first exported as an Objective-C object, and then the Swift compiler copies it one more time for a Swift conversion. This results in additional runtime overhead.
337: 
338: To avoid that, access Kotlin strings in Swift directly as an Objective-C NSString instead. See the conversion example .
339: 
340: NSMutableString
341: 
342: NSMutableString Objective-C class is not available from Kotlin. All instances of NSMutableString are copied when passed to Kotlin.
343: 
344: Collections
345: 
346: Kotlin -> Objective-C -> Swift
347: 
348: When a Kotlin collection is passed to Swift, it's first converted to an Objective-C equivalent, and then the Swift compiler copies the entire collection and converts it into a Swift-native collection as described in the mappings table .
349: 
350: This last conversion leads to performance costs. To prevent this, when using Kotlin collections in Swift, explicitly cast them to their Objective-C counterparts: NSDictionary , NSArray , or NSSet .
351: 
352: See the conversion example
353: 
354: For example, the following Kotlin declaration:
355: 
356: val map: Map<String, String>
357: 
358: In Swift, it looks like this:
359: 
360: map[key]?.count ?? 0
361: 
362: Here, the map is implicitly converted to Swift's Dictionary , and its string values are mapped to Swift's String . This results in a performance cost.
363: 
364: To avoid the conversion, explicitly cast map to Objective-C's NSDictionary and access values as NSString instead:
365: 
366: let nsMap: NSDictionary = map as NSDictionary
367: (nsMap[key] as? NSString)?.length ?? 0
368: 
369: This ensures that the Swift compiler doesn't perform an additional conversion step.
370: 
371: Swift -> Objective-C -> Kotlin
372: 
373: Swift/Objective-C collections are mapped to Kotlin as described in the mappings table , except for NSMutableSet and NSMutableDictionary .
374: 
375: NSMutableSet isn't converted to a Kotlin's MutableSet . To pass an object to Kotlin MutableSet , explicitly create this kind of Kotlin collection. To do this, use, for example, the mutableSetOf() function in Kotlin or the KotlinMutableSet class in Swift and ${prefix}MutableSet in Objective-C ( prefix is the framework names prefix). The same is true for MutableMap .
376: 
377: See an example in the Kotlin-Swift interopedia .
378: 
379: Function types
380: 
381: Kotlin function-typed objects (for example, lambdas) are converted to closures in Swift and blocks in Objective-C. See an example of a Kotlin function with a lambda in the Kotlin-Swift interopedia .
382: 
383: However, there is a difference in how types of parameters and return values are mapped when translating a function and a function type. In the latter case, primitive types are mapped to their boxed representation. Kotlin Unit return value is represented as a corresponding Unit singleton in Swift/Objective-C. The value of this singleton can be retrieved the same way as for any other Kotlin object . See singletons in the table above .
384: 
385: Consider the following Kotlin function:
386: 
387: fun foo(block: (Int) -> Unit) { ... }
388: 
389: It's represented in Swift as follows:
390: 
391: func foo(block: (KotlinInt) -> KotlinUnit)
392: 
393: And you can call it like this:
394: 
395: foo {
396:     bar($0 as! Int32)
397:     return KotlinUnit()
398: }
399: 
400: Explicit parameter names in Objective-C block types
401: 
402: You can add explicit parameter names to Kotlin's function types for exported Objective-C headers. Xcode's autocompletion then suggests these names when calling Objective-C functions in the Objective-C block. This helps to avoid Clang warnings in generated blocks.
403: 
404: To enable explicit parameter names, add the following binary option to your gradle.properties file:
405: 
406: kotlin.native.binary.objcExportBlockExplicitParameterNames=true
407: 
408: For example, for the following Kotlin code:
409: 
410: // Kotlin:
411: fun greetUser(block: (name: String) -> Unit) = block("John")
412: 
413: Kotlin forwards the parameter names from Kotlin function types to Objective-C block types, allowing Xcode to use them in suggestions:
414: 
415: // Objective-C:
416: greetUserBlock:^(NSString *name) {
417:     // ...
418: };
419: 
420: This option affects Objective-C interop only. It applies when calling generated Objective-C code from Objective-C in Xcode, and generally doesn't affect calls from Swift.
421: 
422: Generics
423: 
424: Objective-C supports "lightweight generics" defined in classes, with a relatively limited feature set. Swift can import generics defined on classes to help provide additional type information to the compiler.
425: 
426: Generic feature support for Objective-C and Swift differ from Kotlin, so the translation will inevitably lose some information, but the features supported retain meaningful information.
427: 
428: For specific examples on how to use Kotlin generics in Swift, see the Kotlin-Swift interopedia .
429: 
430: Limitations
431: 
432: Objective-C generics do not support all features of either Kotlin or Swift, so there will be some information lost in the translation.
433: 
434: Generics can only be defined on classes, not on interfaces (protocols in Objective-C and Swift) or functions.
435: 
436: Nullability
437: 
438: Kotlin and Swift both define nullability as part of the type specification, while Objective-C defines nullability on methods and properties of a type. So, the following Kotlin code:
439: 
440: class Sample<T>() {
441:     fun myVal(): T
442: }
443: 
444: In Swift, it looks like this:
445: 
446: class Sample<T>() {
447:     fun myVal(): T?
448: }
449: 
450: To support a potentially nullable type, the Objective-C header needs to define myVal with a nullable return value.
451: 
452: To mitigate this, when defining your generic classes, provide a non-nullable type constraint if the generic type should never be null:
453: 
454: class Sample<T : Any>() {
455:     fun myVal(): T
456: }
457: 
458: That will force the Objective-C header to mark myVal as non-nullable.
459: 
460: Variance
461: 
462: Objective-C allows generics to be declared covariant or contravariant. Swift has no support for variance. Generic classes coming from Objective-C can be force-cast as needed.
463: 
464: data class SomeData(val num: Int = 42) : BaseData()
465: class GenVarOut<out T : Any>(val arg: T)
466: 
467: let variOut = GenVarOut<SomeData>(arg: sd)
468: let variOutAny : GenVarOut<BaseData> = variOut as! GenVarOut<BaseData>
469: 
470: Constraints
471: 
472: In Kotlin, you can provide upper bounds for a generic type. Objective-C also supports this, but that support is unavailable in more complex cases and is currently not supported in the Kotlin - Objective-C interop. The exception here being a non-nullable upper bound will make Objective-C methods/properties non-nullable.
473: 
474: To disable
475: 
476: To have the framework header written without generics, add the following compiler option in your build file:
477: 
478: binaries.framework {
479:     freeCompilerArgs += "-Xno-objc-generics"
480: }

482: Forward declarations
483: 
484: To import forward declarations, use the objcnames.classes and objcnames.protocols packages. For example, to import a objcprotocolName forward declaration declared in an Objective-C library with a library.package , use a special forward declaration package: import objcnames.protocols.objcprotocolName .
485: 
486: Consider two objcinterop libraries: one that uses objcnames.protocols.ForwardDeclaredProtocolProtocol and another with an actual implementation in another package:
487: 
488: // First objcinterop library
489: #import <Foundation/Foundation.h>
490: 
491: @protocol ForwardDeclaredProtocol;
492: 
493: NSString* consumeProtocol(id<ForwardDeclaredProtocol> s) {
494:     return [NSString stringWithUTF8String:"Protocol"];
495: }
496: 
497: // Second objcinterop library
498: // Header:
499: #import <Foundation/Foundation.h>
500: @protocol ForwardDeclaredProtocol
501: @end
502: // Implementation:
503: @interface ForwardDeclaredProtocolImpl : NSObject <ForwardDeclaredProtocol>
504: @end
505: 
506: id<ForwardDeclaredProtocol> produceProtocol() {
507:     return [ForwardDeclaredProtocolImpl new];
508: }
509: 
510: To transfer objects between the two libraries, use an explicit as cast in your Kotlin code:
511: 
512: // Kotlin code:
513: fun test() {
514:     consumeProtocol(produceProtocol() as objcnames.protocols.ForwardDeclaredProtocolProtocol)
515: }
516: 
517: You can only cast to objcnames.protocols.ForwardDeclaredProtocolProtocol from the corresponding real class. Otherwise, you'll get an error.
518: 
519: Casting between mapped types
520: 
521: When writing Kotlin code, an object may need to be converted from a Kotlin type to the equivalent Swift/Objective-C type or vice versa. In this case, you can use the as cast , for example:
522: 
523: @file:Suppress("CAST_NEVER_SUCCEEDS")
524: import platform.Foundation.*
525: 
526: val nsNumber = 42 as NSNumber
527: val nsArray = listOf(1, 2, 3) as NSArray
528: val nsString = "Hello" as NSString
529: val string = nsString as String
530: 
531: IDEs might incorrectly emit "This cast can never succeed" warnings. In such cases, use the @Suppress("CAST_NEVER_SUCCEEDS") annotation.
532: 
533: Subclassing
534: 
535: Subclassing Kotlin classes and interfaces from Swift/Objective-C
536: 
537: Kotlin classes and interfaces can be subclassed by Swift/Objective-C classes and protocols.
538: 
539: Subclassing Swift/Objective-C classes and protocols from Kotlin
540: 
541: Swift/Objective-C classes and protocols can be subclassed with a Kotlin final class. Non- final Kotlin classes inheriting Swift/Objective-C types aren't supported yet, so it is not possible to declare a complex class hierarchy inheriting Swift/Objective-C types.
542: 
543: Normal methods can be overridden using the override Kotlin keyword. In this case, the overriding method must have the same parameter names as the overridden one.
544: 
545: Sometimes it is required to override initializers, for example, when subclassing UIViewController . Initializers imported as Kotlin constructors can be overridden by Kotlin constructors marked with the @OverrideInit annotation:
546: 
547: class ViewController : UIViewController {
548:     @OverrideInit constructor(coder: NSCoder) : super(coder)
549: 
550:     ...
551: }
552: 
553: The overriding constructor must have the same parameter names and types as the overridden one.
554: 
555: To override different methods with clashing Kotlin signatures, you can add the @ObjCSignatureOverride annotation to the class. The annotation instructs the Kotlin compiler to ignore conflicting overloads, in case several functions with the same argument types, but different argument names, are inherited from the Objective-C class.
556: 
557: By default, the Kotlin/Native compiler doesn't allow calling a non-designated Objective-C initializer as a super() constructor. This behavior can be inconvenient if the designated initializers aren't marked properly in the Objective-C library. To disable these compiler checks, add the disableDesignatedInitializerChecks = true to the library's .def file .

560: 
561: See Interoperability with C for an example case where the library uses some plain C features, such as unsafe pointers, structs, and so on.

563: Unsupported
564: 
565: Some features of the Kotlin programming language are not yet mapped into the respective features of Objective-C or Swift. Currently, the following features are not properly exposed in generated framework headers:
566: 
567: Inline classes (arguments are mapped as either underlying primitive type or id )
568: 
569: Custom classes implementing standard Kotlin collection interfaces ( List , Map , Set ) and other special classes
570: 
571: Kotlin subclasses of Objective-C classes
