1: Context parameters
2: 
3: Context parameters replace an older experimental feature called context receivers . You can find their main differences in the design document for context parameters . To migrate from context receivers to context parameters, you can use assisted support in IntelliJ IDEA, as described in the related blog post .
4: 
5: Context parameters allow functions and properties to declare dependencies that are implicitly available in the surrounding context.
6: 
7: With context parameters, you don't need to manually pass around values, such as services or dependencies, that are shared and rarely change across sets of function calls.
8: 
9: To declare context parameters for properties and functions, use the context keyword followed by a list of parameters, with each parameter declared as name: Type . Here is an example with a dependency on the UserService interface:
10: 
11: // UserService defines the dependency required in context 
12: interface UserService {
13:     fun log(message: String)
14:     fun findUserById(id: Int): String
15: }
16: 
17: // Declares a function with a context parameter
18: context(users: UserService)
19: fun outputMessage(message: String) {
20:     // Uses log from the context
21:     users.log("Log: $message")
22: }
23: 
24: // Declares a property with a context parameter
25: context(users: UserService)
26: val firstUser: String
27:     // Uses findUserById from the context    
28:     get() = users.findUserById(1)
29: 
30: fun main() {
31:     val users = object : UserService {
32:         override fun log(message: String) {
33:             println(message)
34:         }
35: 
36:         override fun findUserById(id: Int): String {
37:             return "User $id"
38:         }
39:     }
40: 
41:     context(users) {
42:         outputMessage("Looking up the first user")
43:         println(firstUser)
44:         // User 1
45:     }
46: }
47: 
48: You can use _ as a context parameter name when you don't need to refer to the parameter directly. An anonymous context parameter can still satisfy the context parameters required by called functions, but you can't access it by name. To access its value explicitly, use contextOf<T>() :
49: 
50: // Uses "_" as context parameter name
51: context(_: UserService)
52: fun logWelcome() {
53:     // The anonymous parameter satisfies the UserService context parameter
54:     // required by outputMessage()
55:     outputMessage("Welcome!")
56: 
57:     // Retrieves the UserService value explicitly
58:     contextOf<UserService>().log("Hi!")
59: }

61: Context parameters resolution
62: 
63: Kotlin resolves context parameters at the call site by searching for matching context values in the current scope. Kotlin matches them by their type. If multiple compatible values exist at the same scope level, the compiler reports an ambiguity:
64: 
65: // UserService defines the dependency required in context
66: interface UserService {
67:     fun log(message: String)
68: }
69: 
70: // Declares a function with a context parameter
71: context(users: UserService)
72: fun outputMessage(message: String) {
73:     users.log("Log: $message")
74: }
75: 
76: fun main() {
77:     // Implements UserService 
78:     val serviceA = object : UserService {
79:         override fun log(message: String) = println("A: $message")
80:     }
81: 
82:     // Implements UserService
83:     val serviceB = object : UserService {
84:         override fun log(message: String) = println("B: $message")
85:     }
86: 
87:     // Both serviceA and serviceB match the expected UserService type at the call site
88:     context(serviceA, serviceB) {
89:         // This results in an ambiguity error
90:         outputMessage("This will not compile")
91:     }
92: }
93: 
94: Pass context arguments explicitly
95: 
96: When overloads differ only by context parameters, a call can become ambiguous if multiple matching context values are available.
97: 
98: To resolve the ambiguity, pass an explicit context argument at the call site:
99: 
100: class EmailSender
101: class SmsSender
102: 
103: context(emailSender: EmailSender)
104: fun sendNotification() {
105:     println("Sent email notification")
106: }
107: 
108: context(smsSender: SmsSender)
109: fun sendNotification() {
110:     println("Sent SMS notification")
111: }
112: 
113: context(defaultEmailSender: EmailSender, defaultSmsSender: SmsSender)
114: fun notifyUser() {
115:     // Selects the overload with the EmailSender context parameter
116:     sendNotification(emailSender = defaultEmailSender)
117: 
118:     // Selects the overload with the SmsSender context parameter
119:     sendNotification(smsSender = defaultSmsSender)
120: }
121: 
122: You can also use explicit context arguments to reduce nesting in some function calls:
123: 
124: For a single call, use explicit context arguments to make the call easier to read.
125: 
126: If multiple calls use the same context arguments, use the context() function.
127: 
128: This feature is Experimental . To opt in, add the following compiler option to your build file:
129: 
130: kotlin {
131:     compilerOptions {
132:         freeCompilerArgs.add("-Xexplicit-context-arguments")
133:     }
134: }
135: 
136: <build>
137:     <plugins>
138:         <plugin>
139:             <groupId>org.jetbrains.kotlin</groupId>
140:             <artifactId>kotlin-maven-plugin</artifactId>
141:             <configuration>
142:                 <args>
143:                     <arg>-Xexplicit-context-arguments</arg>
144:                 </args>
145:             </configuration>
146:         </plugin>
147:     </plugins>
148: </build>

150: Restrictions
151: 
152: Context parameters are in continuous improvement, and some of the current restrictions include:
153: 
154: Constructors can't declare context parameters.
155: 
156: Properties with context parameters can't have backing fields or initializers.
157: 
158: Properties with context parameters can't use delegation.
159: 
160: Despite these restrictions, context parameters simplify managing dependencies through simplified dependency injection, improved DSL design, and scoped operations.
