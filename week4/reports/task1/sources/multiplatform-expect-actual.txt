1: Expected and actual declarations
2: 
3: Expected and actual declarations allow you to access platform-specific APIs from Kotlin Multiplatform modules. You can provide platform-agnostic APIs in the common code.
4: 
5: This article describes the language mechanism of expected and actual declarations. For general recommendations on different ways to use platform-specific APIs, see Use platform-specific APIs .
6: 
7: Rules for expected and actual declarations
8: 
9: To define expected and actual declarations, follow these rules:
10: 
11: In the common source set, declare a standard Kotlin construct. This can be a function, property, class, interface, enumeration, or annotation.
12: 
13: Mark this construct with the expect keyword. This is your expected declaration . These declarations can be used in the common code, but shouldn't include any implementation. Instead, the platform-specific code provides this implementation.
14: 
15: In each platform-specific source set, declare the same construct in the same package and mark it with the actual keyword. This is your actual declaration , which typically contains an implementation using platform-specific libraries.
16: 
17: During compilation for a specific target, the compiler tries to match each actual declaration it finds with the corresponding expected declaration in the common code. The compiler ensures that:
18: 
19: Every expected declaration in the common source set has a matching actual declaration in every platform-specific source set.
20: 
21: Expected declarations don't contain any implementation.
22: 
23: Every actual declaration shares the same package as the corresponding expected declaration, such as org.mygroup.myapp.MyType .
24: 
25: While generating the resulting code for different platforms, the Kotlin compiler merges the expected and actual declarations that correspond to each other. It generates one declaration with its actual implementation for each platform. Every use of the expected declaration in the common code calls the correct actual declaration in the resulting platform code.
26: 
27: You can declare actual declarations when you use intermediate source sets shared between different target platforms. Consider, for example, iosMain as an intermediate source set shared between the iosArm64Main and iosSimulatorArm64Main platform source sets. Only iosMain typically contains the actual declarations and not the platform source sets. The Kotlin compiler will then use these actual declarations to produce the resulting code for the corresponding platforms.
28: 
29: The IDE assists with common issues, including:
30: 
31: Missing declarations
32: 
33: Expected declarations that contain implementations
34: 
35: Mismatched declaration signatures
36: 
37: Declarations in different packages
38: 
39: You can also use the IDE to navigate from expected to actual declarations. Select the gutter icon to view actual declarations or use shortcuts .
40: 
41: Different approaches for using expected and actual declarations
42: 
43: Let's explore the different options of using the expect/actual mechanism to solve the problem of accessing platform APIs while still providing a way to work with them in the common code.
44: 
45: Consider a Kotlin Multiplatform project where you need to implement the Identity type, which should contain the user's login name and the current process ID. The project has the commonMain , jvmMain , and nativeMain source sets to make the application work on the JVM and in native environments like iOS.
46: 
47: Expected and actual functions
48: 
49: You can define an Identity type and a factory function buildIdentity() , which is declared in the common source set and implemented differently in platform source sets:
50: 
51: In commonMain , declare a simple type and expect a factory function:
52: 
53: package identity
54: 
55: class Identity(val userName: String, val processID: Long)
56: 
57: expect fun buildIdentity(): Identity
58: 
59: In the jvmMain source set, implement a solution using standard Java libraries:
60: 
61: package identity
62: 
63: import java.lang.System
64: import java.lang.ProcessHandle
65: 
66: actual fun buildIdentity() = Identity(
67:     System.getProperty("user.name") ?: "None",
68:     ProcessHandle.current().pid()
69: )
70: 
71: In the nativeMain source set, implement a solution with POSIX using native dependencies:
72: 
73: package identity
74: 
75: import kotlinx.cinterop.toKString
76: import platform.posix.getlogin
77: import platform.posix.getpid
78: 
79: actual fun buildIdentity() = Identity(
80:     getlogin()?.toKString() ?: "None",
81:     getpid().toLong()
82: )
83: 
84: Here, platform functions return platform-specific Identity instances.
85: 
86: Starting with Kotlin 1.9.0, using getlogin() and getpid() functions requires the @OptIn annotation.
87: 
88: Interfaces with expected and actual functions
89: 
90: If the factory function becomes too large, consider using a common Identity interface and implementing it differently on different platforms.
91: 
92: A buildIdentity() factory function should return Identity , but this time, it's an object implementing the common interface:
93: 
94: In commonMain , define the Identity interface and the buildIdentity() factory function:
95: 
96: // In the commonMain source set:
97: expect fun buildIdentity(): Identity
98: 
99: interface Identity {
100:     val userName: String
101:     val processID: Long
102: }
103: 
104: Create platform-specific implementations of the interface without additional use of expected and actual declarations:
105: 
106: // In the jvmMain source set:
107: actual fun buildIdentity(): Identity = JVMIdentity()
108: 
109: class JVMIdentity(
110:     override val userName: String = System.getProperty("user.name") ?: "none",
111:     override val processID: Long = ProcessHandle.current().pid()
112: ) : Identity
113: 
114: // In the nativeMain source set:
115: actual fun buildIdentity(): Identity = NativeIdentity()
116: 
117: class NativeIdentity(
118:     override val userName: String = getlogin()?.toKString() ?: "None",
119:     override val processID: Long = getpid().toLong()
120: ) : Identity
121: 
122: These platform functions return platform-specific Identity instances, which are implemented as JVMIdentity and NativeIdentity platform types.
123: 
124: Expected and actual properties
125: 
126: You can modify the previous example and expect a val property to store an Identity .
127: 
128: Mark this property as expect val and then actualize it in the platform source sets:
129: 
130: //In commonMain source set:
131: expect val identity: Identity
132: 
133: interface Identity {
134:     val userName: String
135:     val processID: Long
136: }
137: 
138: //In jvmMain source set:
139: actual val identity: Identity = JVMIdentity()
140: 
141: class JVMIdentity(
142:     override val userName: String = System.getProperty("user.name") ?: "none",
143:     override val processID: Long = ProcessHandle.current().pid()
144: ) : Identity
145: 
146: //In nativeMain source set:
147: actual val identity: Identity = NativeIdentity()
148: 
149: class NativeIdentity(
150:     override val userName: String = getlogin()?.toKString() ?: "None",
151:     override val processID: Long = getpid().toLong()
152: ) : Identity
153: 
154: Expected and actual objects
155: 
156: When IdentityBuilder is expected to be a singleton on each platform, you can define it as an expected object and let the platforms actualize it:
157: 
158: // In the commonMain source set:
159: expect object IdentityBuilder {
160:     fun build(): Identity
161: }
162: 
163: class Identity(
164:     val userName: String,
165:     val processID: Long
166: )
167: 
168: // In the jvmMain source set:
169: actual object IdentityBuilder {
170:     actual fun build() = Identity(
171:         System.getProperty("user.name") ?: "none",
172:         ProcessHandle.current().pid()
173:     )
174: }
175: 
176: // In the nativeMain source set:
177: actual object IdentityBuilder {
178:     actual fun build() = Identity(
179:         getlogin()?.toKString() ?: "None",
180:         getpid().toLong()
181:     )
182: }

184: Recommendations on dependency injection
185: 
186: To create a loosely coupled architecture, many Kotlin projects adopt the dependency injection (DI) framework. The DI framework allows injecting dependencies into components based on the current environment.
187: 
188: For example, you might inject different dependencies in testing and in production or when deploying to the cloud compared to hosting locally. As long as a dependency is expressed through an interface, any number of different implementations can be injected, either at compile time or at runtime.
189: 
190: The same principle applies when the dependencies are platform-specific. In the common code, a component can express its dependencies using regular Kotlin interfaces . The DI framework can then be configured to inject a platform-specific implementation, for example, from the JVM or an iOS module.
191: 
192: This means that expected and actual declarations are only needed in the configuration of the DI framework. See Use platform-specific APIs for examples.
193: 
194: With this approach, you can adopt Kotlin Multiplatform simply by using interfaces and factory functions. If you already use the DI framework to manage dependencies in your project, we recommend using the same approach for managing platform dependencies.
195: 
196: Expected and actual classes
197: 
198: Expected and actual classes are in Beta . They are almost stable, but migration steps may be required in the future. We'll do our best to minimize any further changes for you to make.
199: 
200: You can use expected and actual classes to implement the same solution:
201: 
202: // In the commonMain source set:
203: expect class Identity() {
204:     val userName: String
205:     val processID: Int
206: }
207: 
208: // In the jvmMain source set:
209: actual class Identity {
210:     actual val userName: String = System.getProperty("user.name") ?: "None"
211:     actual val processID: Long = ProcessHandle.current().pid()
212: }
213: 
214: // In the nativeMain source set:
215: actual class Identity {
216:     actual val userName: String = getlogin()?.toKString() ?: "None"
217:     actual val processID: Long = getpid().toLong()
218: }
219: 
220: You might have already seen this approach in demonstration materials. However, using classes in simple cases where interfaces would be sufficient is not recommended .
221: 
222: With interfaces, you don't limit your design to one implementation per target platform. Also, it's much easier to substitute a fake implementation in tests or provide multiple implementations on a single platform.
223: 
224: As a general rule, rely on standard language constructs wherever possible instead of using expected and actual declarations.
225: 
226: If you do decide to use expected and actual classes, the Kotlin compiler will warn you about the Beta status of the feature. To suppress this warning, add the following compiler option to your Gradle build file:
227: 
228: kotlin {
229:     compilerOptions {
230:         // Common compiler options applied to all Kotlin source sets
231:         freeCompilerArgs.add("-Xexpect-actual-classes")
232:     }
233: }

235: Inheritance from platform classes
236: 
237: There are special cases when using the expect keyword with classes may be the best approach. Let's say that the Identity type already exists on the JVM:
238: 
239: open class Identity {
240:     val login: String = System.getProperty("user.name") ?: "none"
241:     val pid: Long = ProcessHandle.current().pid()
242: }
243: 
244: To fit it in the existing codebase and frameworks, your implementation of the Identity type can inherit from this type and reuse its functionality:
245: 
246: To solve this problem, declare a class in commonMain using the expect keyword:
247: 
248: expect class CommonIdentity() {
249:     val userName: String
250:     val processID: Long
251: }
252: 
253: In nativeMain , provide an actual declaration that implements the functionality:
254: 
255: actual class CommonIdentity {
256:     actual val userName = getlogin()?.toKString() ?: "None"
257:     actual val processID = getpid().toLong()
258: }
259: 
260: In jvmMain , provide an actual declaration that inherits from the platform-specific base class:
261: 
262: actual class CommonIdentity : Identity() {
263:     actual val userName = login
264:     actual val processID = pid
265: }
266: 
267: Here, the CommonIdentity type is compatible with your own design while taking advantage of the existing type on the JVM.
268: 
269: Application in frameworks
270: 
271: As a framework author, you can also find expected and actual declarations useful for your framework.
272: 
273: If the example above is part of a framework, the user has to derive a type from CommonIdentity to provide a display name.
274: 
275: In this case, the expected declaration is abstract and declares an abstract method:
276: 
277: // In commonMain of the framework codebase:
278: expect abstract class CommonIdentity() {
279:     val userName: String
280:     val processID: Long
281:     abstract val displayName: String
282: }
283: 
284: Similarly, actual implementations are abstract and declare the displayName method:
285: 
286: // In nativeMain of the framework codebase:
287: actual abstract class CommonIdentity {
288:     actual val userName = getlogin()?.toKString() ?: "None"
289:     actual val processID = getpid().toLong()
290:     actual abstract val displayName: String
291: }
292: 
293: // In jvmMain of the framework codebase:
294: actual abstract class CommonIdentity : Identity() {
295:     actual val userName = login
296:     actual val processID = pid
297:     actual abstract val displayName: String
298: }
299: 
300: The framework users need to write common code that inherits from the expected declaration and implement the missing method themselves:
301: 
302: // In commonMain of the users' codebase:
303: class MyCommonIdentity : CommonIdentity() {
304:     override val displayName = "Admin"
305: }

307: Advanced use cases
308: 
309: There are a number of special cases regarding expected and actual declarations.
310: 
311: Using type aliases to satisfy actual declarations
312: 
313: The implementation of an actual declaration does not have to be written from scratch. It can be an existing type, such as a class provided by a third-party library.
314: 
315: You can use this type as long as it meets all the requirements associated with the expected declaration. For example, consider these two expected declarations:
316: 
317: expect enum class Month {
318:     JANUARY, FEBRUARY, MARCH, APRIL, MAY, JUNE, JULY,
319:     AUGUST, SEPTEMBER, OCTOBER, NOVEMBER, DECEMBER
320: }
321: 
322: expect class MyDate {
323:     fun getYear(): Int
324:     fun getMonth(): Month
325:     fun getDayOfMonth(): Int
326: }
327: 
328: Within a JVM module, the java.time.Month enum can be used to implement the first expected declaration and the java.time.LocalDate class to implement the second. However, there's no way to add the actual keyword directly to these types.
329: 
330: Instead, you can use type aliases to connect the expected declarations and the platform-specific types:
331: 
332: actual typealias Month = java.time.Month
333: actual typealias MyDate = java.time.LocalDate
334: 
335: In this case, define the typealias declaration in the same package as the expected declaration and create the referred class elsewhere.
336: 
337: Since the LocalDate type uses the Month enum, you need to declare both of them as expected classes in the common code.
338: 
339: Expanded visibility in actual declarations
340: 
341: You can make actual implementations more visible than the corresponding expected declaration. This is useful if you don't want to expose your API as public for common clients.
342: 
343: Currently, the Kotlin compiler issues an error in the case of visibility changes. You can suppress this error by applying @Suppress("ACTUAL_WITHOUT_EXPECT") to the actual type alias declaration. Starting with Kotlin 2.0, this limitation will not apply.
344: 
345: For example, if you declare the following expected declaration in the common source set:
346: 
347: internal expect class Messenger {
348:     fun sendMessage(message: String)
349: }
350: 
351: You can use the following actual implementation in a platform-specific source set as well:
352: 
353: @Suppress("ACTUAL_WITHOUT_EXPECT")
354: public actual typealias Messenger = MyMessenger
355: 
356: Here, an internal expected class has an actual implementation with an existing public MyMessenger using type aliases.
357: 
358: Additional enumeration entries on actualization
359: 
360: When an enumeration is declared with expect in the common source set, each platform module should have a corresponding actual declaration. These declarations must contain the same enum constants, but they can also have additional constants.
361: 
362: This is useful when you actualize an expected enum with an existing platform enum. For example, consider the following enumeration in the common source set:
363: 
364: // In the commonMain source set:
365: expect enum class Department { IT, HR, Sales }
366: 
367: When you provide an actual declaration for Department in platform source sets, you can add extra constants:
368: 
369: // In the jvmMain source set:
370: actual enum class Department { IT, HR, Sales, Legal }
371: 
372: // In the nativeMain source set:
373: actual enum class Department { IT, HR, Sales, Marketing }
374: 
375: However, in this case, these extra constants in the platform source sets won't match with those in the common code. Therefore, the compiler requires you to handle all additional cases.
376: 
377: The function that implements the when construction on Department requires an else clause:
378: 
379: // An else clause is required:
380: fun matchOnDepartment(dept: Department) {
381:     when (dept) {
382:         Department.IT -> println("The IT Department")
383:         Department.HR -> println("The HR Department")
384:         Department.Sales -> println("The Sales Department")
385:         else -> println("Some other department")
386:     }
387: }
388: 
389: Expected annotation classes
390: 
391: Expected and actual declarations can be used with annotations. For example, you can declare an @XmlSerializable annotation, which must have a corresponding actual declaration in each platform source set:
392: 
393: @Target(AnnotationTarget.CLASS)
394: @Retention(AnnotationRetention.RUNTIME)
395: expect annotation class XmlSerializable()
396: 
397: @XmlSerializable
398: class Person(val name: String, val age: Int)
399: 
400: It might be helpful to reuse existing types on a particular platform. For example, on the JVM, you can define your annotation using the existing type from the JAXB specification :
401: 
402: import javax.xml.bind.annotation.XmlRootElement
403: 
404: actual typealias XmlSerializable = XmlRootElement
405: 
406: There is an additional consideration when using expect with annotation classes. Annotations are used to attach metadata to code and do not appear as types in signatures. It's not essential for an expected annotation to have an actual class on a platform where it's never required.
407: 
408: You only need to provide an actual declaration on platforms where the annotation is used. This behavior isn't enabled by default, and it requires the type to be marked with OptionalExpectation .
409: 
410: Take the @XmlSerializable annotation declared above and add OptionalExpectation :
411: 
412: @OptIn(ExperimentalMultiplatform::class)
413: @Target(AnnotationTarget.CLASS)
414: @Retention(AnnotationRetention.RUNTIME)
415: @OptionalExpectation
416: expect annotation class XmlSerializable()
417: 
418: If an actual declaration is missing on a platform where it's not required, the compiler won't generate an error.
